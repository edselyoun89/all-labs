## 1. MPI + OpenMP

### Требования

Python; только разрешённые библиотеки для вычислений: mpi4py, NumPy, Numba; для графиков matplotlib. threading и multiprocessing запрещены. Нужны случайные входные данные, последовательная и параллельная версии, проверка совпадения, не менее трёх повторов, Barrier до замеров, perf_counter для T1 и MPI.Wtime для Tp. В отчёте требуются S=T1/Tp, E=S/p, B=(1/S-1/p)/(1-1/p), таблицы и три графика. Для варианта 22: метод Якоби, N=2000, 100 итераций, p=1,2,4,8; исследование N_min при E>=0.7.

### Исходная работа варианта 24

Есть MPI-разбиение строк и prange, отчёт, CSV и графики. Подтверждена ошибка выбора ведущего элемента: параллельный алгоритм берёт кандидата только из строки k, не ищет максимум среди строк k..N-1. Контрпример [[0,1],[1,0]]: последовательный результат (-1,0) в формате (знак, ln модуля), параллельный (0,-inf). Проверка выдаёт False. На матрицах с усиленной диагональю дефект скрыт.

Backend Numba первоначально не задан и не проверен; наличие prange само по себе не доказывает OpenMP. Времена в старом отчёте используют разные ядра NumPy/Numba, а выборочное исследование масштабируемости неполно. Объяснение времени Tp стоимостью запуска MPI-процессов неверно: запуск происходит до измеряемого участка. Старый отчёт не содержит полноценного титула и полного кода в приложении.

### Переделка варианта 22

Созданы самостоятельные исходники и отчёты. Использованы одинаковые арифметические циклы в JIT-ядрах последовательного и параллельного методов. Задан backend omp, фактически подтверждён на всех запусках. На процесс выделено два потока, зафиксированы число MPI-процессов и общее число потоков. Матрица строго диагонально преобладает, b создан по известному x*. Выполняются ровно 100 итераций с нулевого приближения. Scatter распределяет строки, Allgather собирает новый вектор после каждой итерации. Tp включает распределение данных, вычисления и обмены и берётся как максимум по rank. Генерация, JIT, проверка и запись файлов исключены.

Основная серия N=2000 выполнена для p=1,2,4,8, по три повтора. Проверка решения использует последовательный метод, известное решение и относительную невязку. Дополнительный тест использует numpy.linalg.solve: обычная и диагональная системы, нулевая правая часть, первая итерация, неделимый размер. Пройдено 19/19 сценариев на p=1,2,4,8. Неправильные параметры завершаются ненулевым кодом.

Поиск N_min начинается с сетки 128,256,512,1000,2000,3000,4000. После первого достижения порога проверены все меньшие допустимые N с шагом p. Экспериментальные минимумы серии: N=124 при p=2 и N=216 при p=4. Для p=8 порог не достигнут на семи размерах основной сетки. Это не доказывает невозможность достижения для любого N. Короткие замеры и минимумы зависят от нагрузки и планировщика ОС; результаты повторных серий могут отличаться.

Поскольку E задания делится на число MPI-процессов при двух потоках на процесс, E может превышать 1; в CSV также сохранена E по 2p потокам. Отрицательные B и B>1 не трактуются как буквальная доля последовательного кода. При p=8 запускаются 16 потоков на машине с 6 физическими / 12 логическими ядрами: это один из вероятных факторов ухудшения наряду с обменами и конкуренцией за память, а не отдельно доказанная причина.

## 2. Потоки

### Требования

Каждый поток — наследник Thread с логикой в run; осмысленное имя; завершение по сигналу и join; документированные функции; logging с временем, именем потока и уровнем; не менее трёх повторов и CSV. Вариант 22 требует PriorityQueue.items, put(task,priority), get(), Condition, HIGH/MEDIUM/LOW, Producer и Consumer, 5 производителей, 10 потребителей, времена по приоритетам и соответствующий график.

### Исходная работа варианта 24

Функционально это другое задание: Scheduler/Task и Timer, отмена одной из десяти задач, оценка точности под нагрузкой. В коде есть полезные Event/Lock и измерение отклонения запуска. Однако time_seq вычислен как сумма задержек, включая отменённую задачу, а не измерен; efficiency делится на число потоков фоновой нагрузки, поэтому эти величины не описывают эффективность планировщика. Между проверкой cancelled и началом функции есть окно гонки, а executed_at фиксируется после завершения функции: cancel может сообщить успех для уже работающей задачи. Эти замечания получены при чтении исходника; отдельный тест гонки не проводился. Новая работа не переиспользует этот планировщик.

### Переделка варианта 22

Самостоятельная min-heap под Condition, стабильный FIFO при равных приоритетах, блокирующее ожидание в while. Все Producer/Consumer — именованные наследники Thread. Сигнал None имеет приоритет бесконечность и ставится после завершения производителей; task_done, queue.join и Thread.join дожидаются окончания. Ошибки рабочих функций возвращаются главному потоку без зависания. Измерены одинаковые наборы задач в последовательном и потоковом режимах. По умолчанию 150 задач по 5 мс имитации I/O; длительность одинакова для всех приоритетов.

Пять тестов прошли: порядок приоритетов и FIFO, блокировка и notify, некорректные параметры/подтверждения, 1500 задач без потерь/дубликатов с 5 производителями и 10 потребителями, возврат ошибки рабочего потока. Основные измерения: 1,2,4,10 потребителей, по три повтора; все 12 запусков корректны. Сохранены 1800 подробных записей задач. Для обязательного режима 10 потребителей среднее время 0.084948 с против последовательного 0.805126 с; S≈9.478. Это перекрытие ожидания I/O, а не свидетельство ускорения CPU-кода Python под GIL.

Отдельно показаны ожидание, обслуживание и полный отклик. Приоритет действует только на уже стоящие задачи; поздняя HIGH-задача не прерывает выполняющуюся LOW. Глобальный порядок завершения не должен использоваться как тест приоритетной очереди. При бесконечном поступлении HIGH возможно голодание LOW; механизм старения не требуется заданием и не реализован.

## 4. Обмен сообщениями MPI

Три подхода присутствуют: Send/Recv с Дейкстрой; коллективные операции с Дейкстрой; одномерная периодическая декартова топология с Флойдом–Уоршеллом и кольцевой передачей строк. Есть генератор графа, CSV и графики. На текущем тесте p=2,N=32,source=0 все три результата совпали с последовательным эталоном.

Подтверждённая ошибка: floyd_cartesian возвращает all_pairs[0], игнорируя --source. При p=2,N=32,source=1 Send/Recv и коллективный метод корректны, cartesian_correct=False, all_correct=False. Программа при этом завершается с кодом 0, что мешает автоматически обнаружить неверный результат по одному коду завершения.

Дополнительные ограничения по коду: разбиение требует делимости N на p; в коллективном методе при несвязном графе rank=0 может выбросить исключение до остальных rank, а point-to-point не имеет согласованного выхода при бесконечном минимуме. Генератор создаёт полный граф с положительными весами и не проверяет эти случаи. Tp не сводится максимумом по процессам и не предваряется Barrier для каждого сравнения; поэтому короткие времена нельзя интерпретировать как строго сопоставимые. Флойд решает все пары, Дейкстра — одну вершину, то есть сравниваются разные объёмы вычислений. Заключение старого отчёта об «оптимальном коллективном подходе при p=8» относится только к сравнению трёх методов при фиксированном p=8, а не к минимальному времени по всем p.

Замечания по коду: recv().decode('utf-8') применяется к произвольному TCP-фрагменту, поэтому разрыв многобайтного символа между recv может вызвать UnicodeDecodeError. Данные, уже пришедшие после hello в том же пакете, обрабатываются только после следующего recv. Ограничения следует учитывать при дальнейшей доработке протокола. Полноценной проверки паролей/учётных записей здесь нет и методичкой геочата она не задана. Для варианта 22 нужен аналитический функционал, которого геочат не реализует.
