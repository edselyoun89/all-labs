3.2. Требования к OpenMP
OpenMP должен быть реализован через библиотеку Numba с использованием декоратора @njit(parallel=True).
Обязательные требования:
Внутри каждого MPI-процесса вычисления должны выполняться параллельно.
Должен использоваться prange для распараллеливания циклов.
Код должен корректно работать с numpy массивами.
Пример правильной реализации:
from numba import njit, prange

@njit(parallel=True)
def parallel_computation(data):
    n = len(data)
    result = np.zeros(n)
    for i in prange(n):
        result[i] = compute(data[i])
    return result

1. ВВЕДЕНИЕ
Умножение матриц является одной из фундаментальных задач вычислительной математики. Для больших размеров матриц (N > 1000) последовательный алгоритм имеет сложность O(N³), что делает его крайне медленным. Параллельные вычисления позволяют значительно ускорить эту операцию за счёт распределения работы между несколькими вычислительными узлами.
Цель данной работы — исследовать эффективность параллельного алгоритма умножения матриц на основе блочного разбиения с использованием технологий MPI (для распределения данных между узлами) и OpenMP (для ускорения вычислений внутри узла).

7. АНАЛИЗ РЕЗУЛЬТАТОВ
7.1. Закон Амдала
Экспериментальная оценка B:
Среднее значение B ≈ 0.145. Это означает, что примерно 14.5% кода выполняется последовательно и не может быть распараллелено. В нашей программе это:
Ввод-вывод (инициализация матриц, вывод результатов).
Распределение блоков (MPI_Scatter).
Сборка результата (MPI_Gather).
Теоретический предел ускорения:
Smax=10.145≈6.90Smax​=0.1451​≈6.90
Экспериментальное ускорение при p = 16 составляет 5.90, что составляет 85% от теоретического предела.
7.2. Эффективность
Причины падения эффективности:
Коммуникационные накладные расходы.
MPI_Bcast и MPI_Sendrecv требуют обмена данными.
При p = 16 количество обменов значительно возрастает.
Дисбаланс нагрузки.
Хотя используется статическое распределение, небольшие вариации во времени выполнения блоков приводят к простоям.
Накладные расходы на синхронизацию.
MPI_Barrier требует синхронизации всех процессов.
7.3. Масштабируемость
Оценка масштабируемости:
Слабая масштабируемость: при p = 2..4 алгоритм хорошо масштабируется (E > 0.8).
Умеренная масштабируемость: при p = 8 эффективность 0.64 — приемлемо.
Плохая масштабируемость: при p = 16 эффективность 0.37 — неэффективно.
Оптимальное число процессов:
Для данной задачи (N = 1024) оптимальное число процессов — 4 или 8. При p = 8 достигается хороший баланс между ускорением (S = 5.10) и эффективностью (E = 0.64).

Ускорение 5.10 при эффективности 0.64.

Алгоритм хорошо масштабируется для умеренных p (2..8).
