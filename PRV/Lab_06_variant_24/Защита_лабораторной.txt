ЛАБОРАТОРНАЯ №6 В ПАПКЕ ПРОЕКТА. ДОКУМЕНТ ОБЩЕГО ДОСТУПА

В исходной методичке эта тема пронумерована как работа №4; таблицы вариантов
нет. Имя папки variant_24 сохранено от организации проекта.

1. КОРОТКИЙ РАССКАЗ

«Я реализовал общий текстовый документ с серверным хранением состояния.
Несколько клиентов подключаются по TCP. Сервер проверяет роли, принимает
редакции и комментарии и рассылает изменения. Чтобы устаревший клиент
не перезаписал чужую редакцию, используется номер версии base_version».

2. КАК ПОКАЗАТЬ

Команды из этой папки, нужен Python с Tkinter.
В первом терминале:
python main.py server --host 127.0.0.1 --port 12346
Первым клиентом подключить администратора:
python main.py client --username Admin
В других терминалах:
python main.py client --username Editor
python main.py client --username Viewer

Первый пользователь свежего сервера получает admin; остальные — viewer.
В Admin указать Editor, выбрать роль editor и нажать «Назначить роль».
В существующем GUI событие role не обновляет локальный self.role:
после назначения ЗАКРЫТЬ Editor и подключить его заново той же командой.
При повторном входе роль читается из сохранённого состояния сервера,
поле редактора становится доступным. Это ограничение текущего интерфейса.

Из Editor написать текст и нажать «Сохранить изменения».
Показать обновление у Admin/Viewer и рост версии. Viewer редактировать
не может. Затем назначить Viewer роль commenter, переподключить его,
добавить комментарий: текст менять нельзя, комментарий разрешён.
Для демонстрации конфликта удобнее запустить автоматический тест:
python integration_test.py
Он отправляет устаревший base_version и проверяет ответ conflict.
После показа закрыть клиентов; сервер остановить Ctrl+C.

3. АРХИТЕКТУРА И РОЛИ

main.py выбирает режим запуска. server.py содержит SharedDocumentServer
и Session, client.py — DocumentClient и DocumentWindow.
Сервер хранит document, version, comments, roles и активные sessions.
К каждому подключению относится отдельный поток. RLock защищает общее
состояние, Lock конкретного сокета защищает отправку JSON-событий.

admin: просмотр, редактирование, комментарии, назначение ролей.
editor: просмотр, редактирование, комментарии.
commenter: просмотр и комментарии.
viewer: только просмотр.
Права проверяются сервером. Отключённая кнопка GUI — удобство интерфейса,
она не заменяет серверную проверку команды.

4. ПРОТОКОЛ И ВЕРСИИ

Двунаправленный TCP, JSON Lines в UTF-8. Каждое событие заканчивается \n.
hello регистрирует имя, edit отправляет полный content и base_version,
comment — номер строки и текст, set_role — имя и роль, state — запрос состояния.
Сервер отвечает welcome/state/document/comment/role/users/error/conflict.

При edit сервер под блокировкой сравнивает base_version с version.
Если они равны и роль позволяет запись, заменяет текст, увеличивает version
и рассылает document. Если версия устарела, возвращает conflict с актуальным
текстом. Это оптимистический контроль конкурентных изменений.
Он обнаруживает конфликт, но не объединяет правки автоматически.
Изменения отправляются при нажатии «Сохранить», а не посимвольно.

5. ЧТО ПРОВЕРЕНО И КАКИЕ ОГРАНИЧЕНИЯ

Проверка 08.11.2026: назначение editor, разрешённая запись, отказ commenter
в редактировании, комментарий и конфликт устаревшей версии — OK.
В тесте пользователь с именем Viewer получает роль commenter; это не
исчерпывающая проверка каждой операции всех четырёх ролей.

Состояние и роли хранятся в памяти; перезапуск сервера их сбрасывает.
Паролей нет: имя — идентификатор, а не подтверждённая учётная запись.
При конфликте GUI загружает текущий текст, сохранение локального черновика
и ручное слияние не реализованы. Проблемы фрагментации UTF-8 аналогичны чату.
Не называть программу посимвольным совместным редактором с CRDT/OT:
здесь передаются полные редакции и проверяется номер версии.

6. ВЕРОЯТНЫЕ ВОПРОСЫ

Почему клиент-серверная модель? Один источник истины для документа,
версии и ACL упрощает согласование состояния и прав.
Что такое ACL? Таблица соответствия пользователей и разрешений/ролей.
Почему одной блокировки мало? Она согласует потоки сервера, но не делает
актуальной копию документа клиента: для неё нужен base_version.
Почему не давать клиенту менять роль самостоятельно? Права назначает admin,
и сервер повторно проверяет каждую команду.
Сохраняются ли данные на диск? Нет, для этого нужен отдельный файл/БД.
Можно ли комментировать без права записи? Да, роль commenter это разрешает.

7. ГОТОВЫЙ ВЫВОД

«Общий документ поддерживает несколько клиентов, разные роли,
комментарии и обнаружение конфликтующих полных редакций.
Сервер проверяет права независимо от интерфейса. Основные сценарии
подтверждены интеграционным тестом».
