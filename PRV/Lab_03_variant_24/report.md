# Лабораторная работа №3

## Титульный лист

**Дисциплина:** Параллельное программирование  
**Тема:** Процессы в Python  
**Вариант:** 24  
**Название:** Параллельный поиск в базе данных

## Задание

Создать базу данных из 10 000 записей, выполнить 10 поисковых запросов, использовать `multiprocessing.Pool` для параллельного выполнения запросов, сравнить результат и время с последовательной версией, измерить работу при разных количествах запросов и процессов, сохранить логи и построить графики.

## Введение

Процессы Python имеют независимые адресные пространства и позволяют использовать несколько ядер CPU без ограничений GIL одного интерпретатора. Однако создание процессов, сериализация аргументов и передача данных между процессами имеют стоимость. Поэтому параллельный поиск полезен только при достаточно тяжёлой обработке каждого запроса или большом объёме данных.

## Теоретическая часть

`multiprocessing.Pool` создаёт фиксированное число дочерних процессов и распределяет между ними задания. В работе используется `Pool.map`: каждый поисковый запрос является отдельным заданием. База данных передаётся процессам через initializer один раз для каждого пула, после чего worker получает только строку запроса.

Ускорение и эффективность вычисляются по формулам:

`S(p) = T_seq / T_par`,

`E(p) = S(p) / p`.

Для каждого набора параметров выполнено три повтора, после чего времена усреднены.

## Алгоритм

1. Сгенерировать 10 000 детерминированных записей с идентификатором, заголовком, категорией и текстом.
2. Сформировать запросы `topic-0` ... `topic-9`.
3. Последовательно просмотреть всю базу для каждого запроса.
4. Создать `multiprocessing.Pool` и передать базу worker-процессам через initializer.
5. Распределить запросы методом `Pool.map`.
6. Сравнить словари результатов последовательной и параллельной версий.
7. Сохранить времена, ускорение, эффективность и количество найденных записей.

## Анализ результатов

Корректность подтверждена во всех 24 отдельных замерах: параллельный поиск возвращает ровно те же идентификаторы записей, что и последовательный.

Для базы из 10 000 записей сами поисковые операции занимают миллисекунды. Поэтому время Pool определяется не сканированием, а созданием процессов, передачей базы при инициализации и межпроцессным обменом. Увеличение числа процессов с 1 до 8 повышает время с `166.165` до `942.829 мс`.

При увеличении числа запросов последовательное время растёт почти линейно: от `2.649` до `25.833 мс`. Время Pool меняется мало, поскольку несколько запросов распределяются по уже созданным процессам, но фиксированные накладные расходы остаются доминирующими.

Практический вывод: для такого маленького поиска параллельная реализация невыгодна. Чтобы Pool дал ускорение, нужно увеличить объём вычислений на один запрос, размер базы, сложность фильтрации или использовать долгоживущий пул вместо создания нового пула для каждого замера.

## Сравнение с лабораторной №2

В [summary.csv второй лабораторной](../Lab_02_variant_24/results/summary.csv) исследовалась точность `Timer` под нагрузкой потоков. В третьей работе исследуются отдельные процессы и накладные расходы `Pool`. В обеих работах результат зависит от стоимости параллельной инфраструктуры: Timer теряет точность при нагрузке, а Pool проигрывает на слишком коротких задачах.

## Выводы

Разработана программа параллельного поиска в базе из 10 000 записей с использованием `multiprocessing.Pool`. Реализованы последовательная версия, параллельная версия, проверка совпадения результатов, три повтора каждого набора, логирование, CSV и графики. Все результаты корректны. На выбранном объёме данных Pool медленнее последовательного поиска из-за стоимости создания процессов и передачи данных; увеличение числа процессов ухудшает время. Это подтверждает необходимость подбирать размер задачи и длительность вычислений с учётом накладных расходов multiprocessing.
