# Лабораторная №2 — вариант 22

Очередь с приоритетами **HIGH, MEDIUM, LOW**. По умолчанию создаются **5 производителей и 10 потребителей** — наследники `threading.Thread`. Очередь реализована самостоятельно на списке-куче, её доступ и ожидание защищены `threading.Condition`.

## Запуск

Из этой папки:

```powershell
python main.py
python main.py --benchmark
..\.venv312\Scripts\python.exe plot_graphs.py
python -m unittest -v test_priority_queue.py
```

Для самого приложения достаточно стандартной библиотеки Python. Для графиков нужен matplotlib (`python -m pip install -r requirements.txt`). В подготовленной среде PRV/.venv312 он уже установлен.

`--tasks 30` — число задач **на одного производителя**, всего 150. `--threads 10` / `--consumers 10` — число потребителей. `--repeats 3` — число повторов (не менее трёх). `--service-ms 5` — одинаковая имитируемая I/O-задержка обработки. `--log DEBUG` включает события каждой задачи. `--benchmark` дополнительно проверяет 1, 2, 4 потребителя.

## Как работает приоритет

Численно HIGH=0, MEDIUM=1, LOW=2. `get()` выбирает задачу с минимальным номером **среди уже находящихся в очереди**. Одинаковые приоритеты обслуживаются в порядке постановки (FIFO), который фиксирует общий счётчик под блокировкой. Уже выполняющаяся LOW-задача не прерывается, если позже поступила HIGH. Поэтому глобальное время завершения задач не обязано строго следовать приоритетам.

`while not items: condition.wait()` освобождает блокировку во время ожидания. `put()` под блокировкой добавляет задачу и делает `notify()`. После завершения производителей главный поток отправляет каждому потребителю `None` с приоритетом бесконечность. Этот сигнал извлекается после обычных задач. `task_done()`, `queue.join()` и `Thread.join()` обеспечивают окончание всей работы.

Сравниваются одинаковые наборы задач, результаты сверяются по каждому ID, проверяется отсутствие потерь и дубликатов. Задержка одинакова для всех приоритетов: преимущество HIGH проявляется в меньшем времени ожидания, а не в искусственно сокращённой длительности обработки. Потоки перекрывают ожидание I/O; результаты не показывают ускорение чистых вычислений Python под GIL. E=S/p считается по числу потребителей; дополнительно в исходных данных указано число всех потоков.

Контрольные вопросы: очередь расширяется ограничением вместимости и отдельным условием ожидания свободного места; голодание LOW при бесконечном потоке HIGH можно уменьшить старением приоритетов; Condition подходит, потому что потребитель ожидает изменения состояния общего списка без активного опроса.
